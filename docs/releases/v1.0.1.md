# APIWatch v1.0.1

A maintenance release with the fixes from a full code review of 1.0.0, including several
security hardening changes. Upgrading is recommended.

APIWatch is a single-user tool for local use. It has no authentication, so do not expose
it to untrusted networks.

## Upgrade notes

- **API clients must send the reviewed fields to approve JSON changes.**
  `POST /api/monitors/{id}/json-baseline/approve` now requires a body with the
  `pending_fields` returned by `GET /api/monitors/{id}/json-baseline`, and answers `409`
  if a newer response has replaced them. This is incompatible with 1.0.0 API clients; the
  dashboard sends the fields itself.
- **JSON inspection requires `GET`.** Creating or saving a monitor with `HEAD` and
  `inspect_json` now returns `422`. Monitors saved this way by 1.0.0 still load; change
  the method or turn inspection off the next time you edit them.
- **JSON numbers have a single type.** Whole numbers and decimals are both `number`, so
  `19.99` → `20` is no longer reported as a change. Baselines saved by 1.0.0 are read
  accordingly.
- **SQLite runs in WAL mode.** While APIWatch runs, `apiwatch.db-wal` and
  `apiwatch.db-shm` sit next to the database, and recent changes may still be in
  `apiwatch.db-wal`. Keep `data/` on a local disk, and stop APIWatch before copying or
  moving the database.
- The new index for failed checks is created on start-up. No migration is needed.

To upgrade a clone, stop APIWatch, run `git pull` and `uv sync`, and start it again.

## Fixes

- URLs the HTTP client cannot send (for example a DEL character or `i❤.ws`) were accepted
  and then crashed every check. They are now rejected when the monitor is saved.
- Database work no longer runs on the event loop, so a slow write or a long dashboard
  query can no longer inflate other checks' response times or make them time out.
- A check's result is discarded instead of being stored under a monitor that was edited,
  or deleted and re-created, while the check was running.
- A monitor whose host stopped resolving can be paused and edited again.
- Turning JSON inspection off no longer deletes the baseline, so changes made meanwhile
  are reported instead of silently accepted.
- Deeply nested JSON no longer crashes a check, and errors while reading a body for JSON
  inspection no longer turn a `200` into DOWN.
- `python -m app.database` now creates the tables.
- Dashboard: refreshes are queued instead of dropped, polling pauses in hidden tabs, and
  the incident count, chart labels and the 404 page's "Add monitor" button are fixed.

## Security

- Cookies are never stored or sent. Requests go to pinned IP addresses, so a cookie set by
  one monitored host could otherwise reach another hostname on the same address.
- International host names are resolved by their IDNA 2008 name, the one sent as `Host`
  and TLS SNI. Before, `straße.de` could be pinned to the address of `strasse.de`.
- Response bodies are requested uncompressed, and compressed bodies are inflated only up
  to the response size limit.
- IPv6 ranges that embed IPv4 addresses (6to4, Teredo, NAT64, IPv4-compatible) are blocked
  explicitly. On Python 3.12.0–3.12.3, 6to4 addresses counted as public.
- Error messages that could quote response bytes are replaced by fixed text before they
  are stored.
- DNS lookups run in a dedicated thread pool, so hung lookups cannot starve other work.

These measures reduce SSRF risk. They do not remove it entirely: for example, a public
host that relays requests into a private network cannot be detected. See the
"Security and deployment limitations" section of the README and `SECURITY.md`.

## Requirements and installation

- Python 3.12 or 3.13 (tested in CI) and [uv](https://docs.astral.sh/uv/).

```bash
git clone https://github.com/berkdogutan/ApiWatch.git
cd ApiWatch
uv sync
uv run apiwatch            # http://127.0.0.1:8000
```

The README describes the offline demo (`demo.mock_api` and `demo.seed`).

## Known limitations

- Run a single Uvicorn worker. Multiple workers or replicas duplicate scheduled checks.
- No authentication, notifications, history retention or schema migrations.
- Only `GET`/`HEAD` without custom headers. JSON comparison covers top-level fields only.
